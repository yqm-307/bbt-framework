# bbt-framework 分布式服务端框架：架构基调

状态：**架构基调 v0.1，作为当前设计真源生效；不冻结具体 API、第三方依赖或实现完成度。**

日期：2026-09-24。用户明确目标：framework 后续基于 infra 实现为分布式服务端框架，本轮确定架构基调。

## 0. 一句话定位

**在 bbtools-infra 之上，构建以 Service 为业务边界、以显式远程调用语义为基础、以可选 Actor 执行和有状态扩展为补充的 C++ 分布式服务端框架。**

框架应给业务提供“可运行、可扩容、可诊断、可安全退出”的服务模型，而不是要求业务自己拼接网络库；但不把共识数据库、消息系统、集群调度器和工作流引擎全部重做一遍。

基调：**统一语义，限制隐式行为；核心小而完整，扩展按需求接入；先无状态多实例，再有状态归属；故障行为先于性能优化。**

以下规范性措辞都是设计建议。标注 `[L…]` 的事实来自本地已读代码/契约，`[E…]` 来自公开原始资料；来源索引见 [`distributed-framework-evidence.md`](./distributed-framework-evidence.md)。其余为本研究提出的取舍，不是对现有能力的断言。

已读代码表明：

- `CoApp` 已装配真实 HTTP 宿主和出站桥，按服务名查静态路由；不能再把整个仓库描述为“尚无构建入口”。`AGENTS.md` 中该旧进度与 README 有冲突，本次落库同步修正。[L01,L02,L03]
- `CallOptionsAdapter` 已实施父子 deadline 取最小、顶层必须有限预算、出站前过期拒绝和取消合并；不是从零设计上下文。[L04]
- `RequestScope` 以协程 id 维护请求上下文，非协程场景另按 thread id；需要保护这个语义，不把普通 thread_local 当请求作用域。[L05]
- `ActorMailbox` 是一个本地单消费者 drain coroutine，handler 挂起时不释放该 Actor 的执行资格。它是执行策略，不是跨节点目录或分布式唯一 owner 的证明。[L06]
- `OrderedIngress` 有授权流、sequence、in-flight 和有界终态缓存；同流的旧序号在途返回 InProgress，终态重放，淘汰后 ResultExpired，不重新执行。这里使用本地内存容器，不能据此宣称跨重启/跨迁移 exactly-once。[L07,L08]
- `OutcomeUnknown` 已在 infra 错误枚举中。下一步应核对传播与使用规则，不重复发明同义错误体系。[L09]
- infra ADR 0006 已明确基础配置源/版本化快照/watch 与 framework 配置治理的分工，但状态写的是“已确认方向，待按此实现”，不能把目标目录/API 当现有实现。[L10]

结论：不是重搭一套框架，而是把已有“单进程服务运行语义”扩展为“多实例服务语义”，并单独处理状态权威。

## 2. 总体分层：一个应用模型，两类平面，明确依赖方向

```text
应用：业务 Service、领域协议、业务状态、授权规则、补偿逻辑
                         ↓
framework 核心：CoApp / Service / RequestContext / 生命周期
               逻辑寻址与调用策略 / 接纳控制 / 资源编排 / 诊断
                         ↑ 使用公开扩展契约
framework 扩展：注册发现 provider、分片/owner、消息、工作流、观测 exporter
                         ↓
infra：协议/transport、客户端 adapter、编码、连接与 I/O 资源生命周期
       基础配置快照与 watch、错误映射、第三方执行域桥接
                         ↓
coroutine：调度、等待/唤醒、deadline/cancellation、executor
```

上图中的扩展依赖核心公开契约，核心不反向依赖某个具体扩展；装配由应用完成。运行时调用 provider 不是构建依赖反转。

### 数据面

每次业务请求的解析、身份校验结果接收、路由、接纳、执行、回复。数据面不应每次 RPC 都同步查询注册中心；读取已经安装的不可变路由/配置视图。

### 控制面

服务注册、发现变更、资源配置、分片归属、版本发布和停机协调。控制面异步更新数据面视图；需要权威性的决定必须使用具备相应保证的存储或协调服务。

**控制面故障不等于所有无状态调用立即失效，也不意味着有状态写入可以无条件继续。** 两者策略必须分开：前者可在显式期限内沿用 last-known-good 视图，后者仍须满足当前写入权威/令牌验证。

### 分工表

| 能力 | infra 负责 | framework 负责 | 应用负责 |
|---|---|---|---|
| RPC | 线上编码、传输、连接、I/O 取消与错误事实 | 逻辑服务调用、策略、上下文、路由、治理 | 方法/请求/回复及副作用语义 |
| 发现 | 后端客户端、watch/CAS 等基础机制 | 注册生命周期、实例视图、路由更新与陈旧策略 | namespace、部署与可用性选择 |
| 配置 | 读取、版本观察、通知与关闭 | schema、校验、资源版本切换、回滚编排 | 业务配置约束 |
| 身份 | TLS/凭证验证、可信 transport identity | service/method/tenant 授权执行点 | 领域资源授权 |
| 状态 | 数据库/日志/协调后端 adapter | 可选 owner/fencing/state 扩展 | 一致性目标、事务边界、恢复策略 |
| 运行时 | 第三方回调桥接、资源 I/O 寿命 | 请求/Service/App 寿命与停机顺序 | 不脱离作用域制造失管任务 |

共享运行时不等于“系统只能有一个线程”：复用既有 executor，不因增加扩展偷偷再建一套 I/O 调度器；确有阻塞 driver 时，使用 infra 拥有的、配置可见的有界 worker bridge。[L10]

## 3. 框架核心要完整，但不做插件平台大工程

首批核心能力建议只有七组：

1. **Host 与生命周期**：装配、启动、就绪、接纳、排空、资源释放。
2. **Service 与方法契约**：服务名、方法名、schema、执行策略、调用权限和方法幂等属性。
3. **Call/RequestContext**：预算、取消、逻辑 operation 标识、attempt、trace、已验证调用身份。
4. **Resolver/Router**：把逻辑目标解析成一组候选实例，按调用类型选路由。
5. **Admission 与资源边界**：服务并发、Actor 邮箱、出站并发、连接/字节/等待队列上限。
6. **配置与资源编排**：不可变版本、预检、安装、旧实例排空、失败回退。
7. **诊断语义**：稳定错误、指标、请求事件及追踪扩展点。

“核心能力”不意味着一个巨型类；实现应分成可单测的小状态机与持有 I/O 的外壳。先做实际需要的窄 provider 接口；不预建动态插件 ABI、任意 middleware DAG 或全能 service locator。

默认发行组合可以包含静态发现和一种经过验收的真实注册后端；核心不硬编码某家后端，也不要求为了运行 echo 服务先部署 Kafka、etcd、Temporal 全家桶。

## 4. 先把请求语义固定下来

### 4.1 本地与远程保持同一套业务契约，但不伪装同一成本和失败模型

业务通过服务/方法逻辑地址调用，不依赖 endpoint。即使目标恰在同一进程，也要经过相同的授权、预算、接纳、执行策略与错误边界；可以有本地快速路径，但不能通过直接函数调用绕过这些约束。

入站建议路径：

```text
infra 解码与长度边界 → 可信身份上下文 → 协议/schema/路由校验
→ 授权 → 接纳与执行资格 → 建立 RequestScope → handler
→ 规范化终态 → 回复/诊断 → 释放请求资源
```

出站建议路径：

```text
读取 RequestContext → 收紧预算与合并取消 → 方法策略
→ 读取版本化 endpoint/owner 视图 → 选目标 → 接纳出站 attempt
→ infra 发送 → 解释回复或未知结果 → 必要时按策略重试 → 一个调用终态
```

“调用终态”与“远端操作终态”不能混用：调用者超时后停止等待，远端仍可能完成业务副作用。

### 4.2 标识必须分清

- **operation_id / 幂等键**：同一次逻辑业务操作的重试共用，作用域绑定 tenant、caller、service/method 与请求摘要。
- **attempt_id**：一次传输尝试，用于诊断、取消与在途计数，不能代替业务幂等键。
- **request_id**：现有线上字段先保留；是否直接承载 operation_id 要核对既有调用者，不能静默改含义。[L11]
- **trace_id**：观测关联，不是授权凭证、幂等依据或顺序号。
- **producer_epoch / receiver_epoch**：会话代际，不自动等同于分布式 owner token。[L08]
- **owner generation / fencing token**：由权威服务或存储认可的所有权代际；不能由节点自行随机生成后假设具备可比较权威。

幂等键同名却 payload 不同必须拒绝；“返回同一个业务结果”与“避免再次执行”也不同，缓存淘汰可以保留去重水位而不再保存结果。

### 4.3 Deadline 与 cancellation

保留现有 min(parent, child) 和取消合并。用本地单调时钟管理本地 deadline；不得把某台机器的 `steady_clock::time_point` 原值发给另一台。[L04,E01]

线上传播剩余预算，接收方与自己的上限取较小值，再映射为本地期限。发送前扣除本地已耗时间；客户端始终执行原始总 deadline。需要诚实写明：没有时钟/传输时延额外约束，仅传 TTL 不能证明在任意网络延迟下所有远端副作用都在原始截止时刻前终止。

Cancellation 是停止继续工作/等待的请求，不是事务回滚凭证；已经提交的数据库写入不能因为 RPC cancel 就被当作没发生。下游资源释放以实际 completion/close 确认为准。

### 4.4 错误按“是否有结果证据”处理，不靠错误名字猜重试

| 已知事实 | 返回/处理原则 |
|---|---|
| 出站前本地校验失败、预算已过、无法入队 | 明确本次未发起；修正输入/预算，不盲重试 |
| 下游明确未接纳 | 可按其契约退避；总预算和容量仍约束重试 |
| 收到可信业务终态 | 返回终态，不把任意业务失败升级为网络重试 |
| 可能到达且回复未知 | 保留 OutcomeUnknown/结构化未知事实；查询业务状态或用同一幂等键按既定协议恢复 |
| 去重状态存在但结果已淘汰 | ResultExpired；不重新执行假装获得结果 |

`TimedOut`、`TransportError` 本身通常不足以决定是否执行过。若 infra 无法给出执行证据，framework 必须保守处理，不能从 `transferred_bytes` 推导远端提交事实。[L09]

### 4.5 重试默认关闭，逐方法开放

默认一次业务尝试。开启前明确方法属于只读、天然幂等、持久幂等键保护，还是不可安全重试；依据实际语义，不以 GET/POST 名称替代。

选定一个重试责任层；与代理和底层库的透明 retry 行为一起核对。限制 attempts、累计 retry budget、出站并发和整体 deadline；指数退避加 jitter。hedging 独立 opt-in，首阶段不默认开启。gRPC 已有 retry policy、commit point、退避和服务端推回机制，值得借鉴的是边界而非默认参数。[E02]

不要把“所有超时先查询一次”做成全局硬规则：没有权威查询接口时查不到最终结果；查询失败仍然未知。协议允许的同幂等键重发也是一种恢复方式。

## 5. 发现、路由与故障切换不能混成一个功能

### 5.1 名字、实例、健康与权威分开

逻辑服务名不含物理地址；实例标识必须包含重启代际，避免 IP/端口复用导致旧连接/旧状态认成新进程。endpoint view 携带 revision、来源、安装版本、观测时间及陈旧状态。健康探测只提供某观察者的可达性事实，不授予写入权威。

### 5.2 版本化 snapshot + watch

静态路由也适配成一个不可变 snapshot，先统一读取路径，再接动态发现。对于支持 revision 的后端：取得快照及 R，从 R 后续订阅，校验来源与版本，原子安装完整新视图；断线保留明确 stale 状态；历史已压缩时重取快照，不猜补漏。

etcd 的 watch 提供可恢复的修订序事件，但不承诺线性一致读取或固定投递延迟；因此“watch 没通知撤销”不能作为持有写权的证据。[E03]

不同 provider 的 revision 不可直接比大小；重置/恢复需要 provider epoch 或 reset 事件。不要把“版本字符串不同”当成“版本一定更新”。

### 5.3 先做少数清晰的路由策略

- 无状态服务：首版 round-robin 或简单权重策略即可；基于实际请求完成更新在途计数，后续再评估 power-of-two/least-loaded。
- 本地 key 串行服务：Actor key 决定本地执行单元；跨节点如何选 owner 仍是另一层。
- 需要 affinity 但状态可丢/可重建：可用 rendezvous/consistent hashing，明确重映射不保证状态转移。
- 强单 owner 状态：通过权威 owner 记录决定归属，路由缓存只是提示；接收端及最终资源仍验证代际。

无状态请求换实例与有状态命令转发不可使用同一个自动 failover 开关。跳转带上限，避免旧目录互相重定向；调用的总预算不随跳转重置。

## 6. Actor 是可选执行模型，不是整个框架的信仰

继续支持 Concurrent 与 ActorSerial。无状态 Service 可以并发；同 key 串行解决单进程内可变状态访问，不能解决跨进程分区、目录漂移或持久化。[L06,L12]

默认 ActorSerial 非重入，挂起时保持执行资格；这一选择易理解但会产生 A 等 B、B 再等 A 的调用环风险。文档显式禁止依赖同 Actor 队列后续消息才能完成的同步等待；通过 deadline、可诊断调用链和特定工作流设计处理，而不是悄悄开启重入。[L06]

Orleans 的价值在于把位置、激活和运行时管理纳入系统设计，不意味着只实现 mailbox 就得到了虚拟 Actor 系统。[E04]

### 三类状态必须显式选择

| 状态类别 | 宕机含义 | 框架承诺 |
|---|---|---|
| 请求临时/缓存 | 可以丢失或重建 | 不承诺持久、迁移和全局唯一 |
| 外部存储持久状态 | 数据库是权威 | Service/Actor 协调访问，不替代数据库事务 |
| 带 owner 的分片/Actor 持久状态 | 需要归属恢复与旧 owner 拒绝 | 作为单独扩展，经故障验收后承诺 |

### 单 owner 的最小安全故事

建议采用成熟协调后端分配可验证的 ownership generation；由最终接受写入的资源在同一原子边界验证 generation 并完成写入。旧 owner 即使长暂停后苏醒，也不能写入新一代资源。

只在 RPC 网关看 token 而数据库写不检查，仍可能被已经入队或越过检查点的旧任务写入。资源不支持 fencing/CAS/事务时，必须降低承诺，不能靠框架声明填补原子性缺口。

接管至少包含：取得新权威 → 建立写屏障 → 恢复持久状态及所需去重/序号信息 → 发布可服务状态。具体提交/屏障顺序须建模，不能把这四个词当成可直接编码的完整协议。

**本期不默认实现 Actor 在线迁移、自动全局唯一激活、跨区多主和分片复制。** 如果产品场景确实需要，先拿一个最小有状态业务证明恢复与 fencing，而非预建分布式对象平台。

## 7. 一致性与事务按对象选择，不全框架一刀切

建议默认采用单区域、多实例部署，面向进程崩溃、重启、消息延迟/丢失/重复和网络分区；身份认证和输入验证仍然必需。拜占庭共识、多地域 active-active 不在初期承诺。并未因“内部服务”假设所有输入都可信。

- 路由/配置：版本可见、允许受控陈旧；需要权限撤销等强约束的字段采用更严格策略。
- owner/关键协调状态：需要线性化条件更新或等效机制；不让 gossip/hash ring 承担权威职责。
- 业务数据：由具体方法/存储给出事务、版本或最终一致性契约；不能因为注册中心有 Raft，就宣称所有业务调用线性一致。
- 跨服务流程：默认不提供透明分布式事务。优先让业务不变量留在一个清晰事务边界；再评估 outbox/inbox、幂等与补偿，Saga 补偿不是数据库 rollback。

“绝不使用 2PC”也过于绝对。成熟分布式数据库可以在明确的复制、事务与时钟假设下提供强事务；是否消费这样的数据库，与是否在服务框架内自研事务协调器是两件事。[E05]

Raft 的复制日志/安全规则可以作为理解权威状态的基础，但一个 Raft 库不自动提供发现、ACL、持久业务状态或任意外部副作用 exactly-once。[E06]

## 8. 背压、停机和资源版本属于同一类所有权问题

### 背压

每个可积压点必须有单位明确的上限：连接、请求、字节、Actor 数量、单 Actor 邮箱、出站 attempt、阻塞桥 worker、结果缓存以及 watcher 更新积压。

先做固定上限、拒绝和可观测性；自适应限流、熔断和 outlier detection 后置。接纳计数到实际工作/资源结束再释放，不能 RPC 先超时就把仍执行的工作当作空闲容量。

Envoy 区分面向上游调用的 circuit breaking 与面向本进程资源耗尽的 overload management；框架也不应用一个“熔断开关”混管这些边界。[E07]

### 启停顺序

建议启动：装配校验 → runtime/infra 资源 → 安装 handler → listener 就绪但业务未 ready → 依赖与发现能力就绪 → 发布 ready/实例 → 开放正常接纳。发布失败不对外宣称可服务。

建议停机：本地 readiness 关闭/拒新 → 发布 draining 或注销（尽力但有期限）→ 等待/取消既有工作 → 关闭 transport 与所有 provider → 确认 completion/close → 释放服务与资源 → 停 runtime。

发现变更存在延迟，所以不能等远端都看见注销再本地拒新。数据面必须能对到达旧实例的新请求给出明确拒绝，状态调用不自动跨 owner 重放。

现有 `HostLifecycle` 超过优雅关闭预算会标记 incomplete 然后无界续等，避免未关闭资源被释放。[L13] 将来必须明确区分：

1. 进程内安全收口是否完成；
2. 编排系统给进程的硬退出时限。

硬截止由 supervisor/运维策略执行，可能牺牲未完成请求；不能在 framework 内以“强制释放仍有回调引用的对象”伪装优雅关闭。

### 配置与资源切换

新配置读取 → schema/安全/范围校验 → 预建资源版本 → 原子安装新引用 → 旧版本拒绝新借用并排空 → 关闭。请求持有自己使用的资源版本，不读到半新半旧配置。连接凭证/地址更新不能等价于覆盖结构体几个字段。[L10]

安全撤销不一定适合 last-known-good：证书撤销/授权策略失效的处置需与普通流量权重配置区别设计。

## 9. 安全、协议兼容与观测从第一期纳入

- `peer_principal` 来自经过认证的通道/可信 adapter，不从普通 metadata 抄入。[L11]
- `fw.*` 只是保留字段命名，客户端可以构造线上字节；真正授权必须接收端验证，不能以“C++ 私有构造函数不可调用”证明线上不可伪造。
- 业务 route/custom 与系统 metadata 分开，限制大小、重复键、编码和允许值；owner token、trace 与幂等键均不能作为身份认证替代品。
- wire version、schema 兼容、稳定错误编码和 unknown field 策略必须有明文定义；不能把 C++ enum 的当前整数顺序当永久跨版本协议。
- 每次请求记录 method、operation/attempt、选中实例及代际、route/config revision、队列时间、执行时间、结果知识状态。指标标签不放用户 id/actor key/request id，避免高基数。
- 服务健康拆成 liveness、readiness、draining 与控制面陈旧；“进程活着”不等于“可承接新的有状态写入”。

已读 `RpcHttpBridge` 只是在当前代码位置承担 HTTP/RPC 映射，本轮不直接迁移它。后续应把稳定 wire 编码/验证收敛给 infra，framework 保留组装与策略，迁移须对已有消费者兼容。[L14]

需要补证的协议问题：现有桥的显式请求头没有列出跨进程 budget 字段；错误回复只列 code/domain/domain_code/message。应以完整集成链实测核对预算和结构化 details 是否保真，不能因内存类型有字段就宣称线上具备。[L11,L14]

## 10. 实施路线：用场景收敛，不按框架名堆功能

| 阶段 | 交付场景 | 验收门槛 | 不顺带做 |
|---|---|---|---|
| P0 契约收口 | 当前本地/HTTP 调用有明确预算、未知结果、身份/错误传播、关停语义 | 真实两进程请求及错误/取消/慢关闭；保留已有 API 与行为证据 | 新共识/新 Actor 平台 |
| P1 无状态多实例 | 一调用方、两服务实例，动态发现与简单负载均衡，滚动退出 | kill/restart、watch 断线/压缩恢复、陈旧视图、过载拒绝，调用预算不因重试重置 | 自动迁移/跨区复制 |
| P2 有状态最小切片 | 一个 key 对应权威 owner，外部持久存储、接管、旧 owner 拒绝 | 分区后旧节点恢复、回复丢失、崩溃窗口；不能双写 | 通用在线迁移/全局事务 |
| P3 按业务扩展 | 某个真实异步业务的 outbox/inbox 或工作流 | 重复投递、消息重放、补偿失败、版本升级有 oracle | 通用消息平台/全能 DAG 引擎 |
| P4 性能与运维增强 | 基于实际 workload 优化发现 fanout、队列和 tail latency | 负载曲线、排队/执行分解、资源成本，正确性测试不退化 | 无数据的“高性能”宣称 |

P0/P1 的实现顺序是当前建议，不代表具体实现任务已自动获批；进入实现前仍须按仓库流程确认范围、契约与验收。具体注册后端、TLS/身份接入、状态存储要结合第一真实业务及依赖评估确认；研究对象不是依赖清单。

## 11. 从现在就预留的可验证边界

纯策略/状态机输入：时钟读数、随机数、发现事件、请求/完成事件；输出：发出请求、设置计时器、安装视图、拒绝、记录终态。避免在策略内部直接散落系统时钟和隐式全局 I/O。

但不以此宣称现有 C++ 运行时/第三方 driver 可整体确定性模拟。测试拆三层：

1. **有界模型/属性测试**：重试预算不超限、至多一个调用终态、旧版本不覆盖新视图、同幂等键冲突被拒绝、owner 写屏障。
2. **真实协程与 adapter 测试**：跨 worker 上下文、超时/完成竞争、晚到回调、buffer/socket/request 寿命、有界队列与关闭。
3. **真实跨进程故障测试**：partition、kill/restart、watch compaction、外部提交后响应丢失、资源恢复。

FoundationDB 的仿真方法之所以有价值，在于系统性控制非确定性和检查不变量，不是“多随机跑几次”；本框架先复制测试边界设计，不承诺复制整个仿真平台。[E08]

首批 30 项测试编号与 oracle 见 `distributed-framework-validation-matrix.md`；均为尚未执行的测试设计。五路专题研究报告已完成并完成基础结构核验，但其中部分源码路径、论文范围和真实行为仍按各报告的“未覆盖/待验证”声明处理，不能把静态源码阅读写成运行验证。所有分布式承诺都要有历史记录和可判定的反例；延迟和吞吐结论必须来自真实 workload 实测。

## 12. 建议本轮确定与暂不确定的事项

### 建议确定的基调

- 定位分布式服务端框架，不退化为网络库工具箱，也不扩成通用分布式操作系统。
- Service-first，Actor optional；分开本地执行串行与跨节点权威。
- infra 管机制与底层资源，framework 管服务语义与编排，应用管业务不变量。
- 远程失败、OutcomeUnknown、显式预算、幂等边界、有界资源、安全关闭是基础能力。
- 无状态多实例先形成真实闭环；强状态能力经单独协议和故障证明推进。
- 学习成熟实现的边界和不变量，而不是按功能表重新造所有中间件。

### 暂不冻结

- 具体注册中心及客户端库，是否依赖外部部署平台。
- 持久 Actor 是否为首个真实需求、状态存储和恢复方式。
- 全局 owner 协议、fencing 的最终执行点以及跨资源事务边界。
- wire v2、IDL/codegen 形式、调用元数据扩展的最终公开签名。
- 无数据支撑的线程数量、连接池尺寸、重试次数、吞吐目标。

这些开放项不阻止确定基调；进入相应实施阶段时再形成有证据的 ADR。


## 13. 真源与变更规则

本文件是 `bbt-framework` 分布式服务端框架的架构基调真源；验收场景见配套矩阵，源码与外部资料证据见配套证据索引。具体 API、依赖、注册中心、状态存储和实现顺序必须在对应实现任务或 ADR 中单独确认，不得通过修改本文件偷偷冻结。

若实现、测试或后续 ADR 发现与本基调冲突，先记录冲突和证据，再更新本文件或明确局部例外；不得把局部实现反向包装成框架级保证。
